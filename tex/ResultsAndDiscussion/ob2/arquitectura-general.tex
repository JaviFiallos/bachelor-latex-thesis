\paragraph{Diagrama de contenedores}

La aplicación web se ejecuta en el navegador de cada usuario; los demás contenedores se ejecutan en un único servidor virtual mediante Docker Compose (Figura~\ref{fig:ob2_c4_contenedores} y Tabla~\ref{tab:ob2_contenedores}). El proxy inverso es la única entrada pública: dirige la aplicación web y la API, y entrega el webhook al servicio del agente. La API concentra la lógica y las reglas del sistema; el servicio del agente conversa con el paciente y opera sobre la agenda solo a través de una interfaz interna de la API, que no se expone a internet. \paragraph{Estilo arquitectónico de la API: monolito modular}

La API se organiza como un monolito modular: una sola aplicación, desplegada como una unidad, cuyo código se divide en módulos por área funcional \cite{richards2020fundamentals}. Los antecedentes separan cada capacidad en un microservicio \cite{roca2020microservice,arcila2022microservice}. En una clínica pequeña, con un único desarrollador y un único servidor, esa separación añadiría despliegues, comunicación por red y monitoreo por servicio, una complejidad sin beneficio proporcional. De \cite{roca2020microservice} se conserva la idea de añadir capacidades sin modificar el núcleo, y de \cite{arcila2022microservice}, la autenticación con JWT. El servicio del agente es el único componente fuera de la API; se separa para aislar el procesamiento del texto libre de los datos de la clínica, no por escala.

La Figura~\ref{fig:ob2_modulos} agrupa los módulos esenciales y muestra cómo se comunican. La Tabla~\ref{tab:ob2_modulos} resume qué hace cada uno.

Cada módulo expone una interfaz pública y no accede al interior de los demás. Los cambios de la agenda, como crear o reprogramar una cita, se publican como eventos que programan los recordatorios. Así, un cambio en las reglas de agendamiento no altera la conversación del agente. La auditoría (RNF02) es transversal y no forma un módulo. La separación no es completa: los módulos comparten la base de datos, de modo que un cambio de tabla puede afectar a más de uno.

\paragraph{Estructura de la aplicación web}

La aplicación web es una aplicación de una sola página organizada por funcionalidades que replican los módulos de la API: agenda, pacientes, clínico, cobros y dirección. Una capa base gestiona la sesión, adjunta el token a cada petición y restringe las rutas por perfil; los componentes compartidos, como el selector de horarios o el panel lateral, se reutilizan entre funcionalidades.
