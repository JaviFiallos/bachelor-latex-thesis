\subsubsection{Construcción de la base del proyecto}

La construcción comenzó por la base común sobre la que se desarrollaron las demás tarjetas del plan (Tabla~\ref{tab:ob2_tarjetas}): la estructura de la API y de la interfaz web, el esquema versionado de la base de datos y el entorno de pruebas.

\paragraph{Estructura de la API y de la interfaz web}

La API mantiene el monolito modular del diseño (Figura~\ref{fig:ob2_modulos}): un paquete por módulo, con tres capas internas (\texttt{api}, controladores; \texttt{application}, servicios y transacciones; \texttt{domain}, entidades y reglas) y una interfaz pública para los demás módulos. La Figura~\ref{fig:ob3_arbol_api} muestra esta estructura en el módulo de agenda; los demás módulos la repiten.

La interfaz web replica esa división (Figura~\ref{fig:ob3_arbol_web}): una carpeta por funcionalidad, con sus páginas, componentes, servicios de acceso a la API y modelos. La capa \texttt{core} gestiona la sesión, adjunta el token a cada petición y restringe las rutas por perfil.

En desarrollo, la interfaz web se sirve con el servidor de Angular y un proxy dirige \texttt{/api} a la API local; PostgreSQL corre en un contenedor, y el webhook usa el número de prueba de Meta y un túnel temporal (Tabla~\ref{tab:ob2_webhook}).

\paragraph{Esquema versionado}

Flyway crea el esquema con migraciones numeradas que se versionan junto al código y se aplican al arrancar la API. Cada tarjeta añadió la migración de su grupo de tablas (V1 a V22; apartado siguiente).

\paragraph{Pruebas}

Cada tarjeta incorporó sus pruebas: unitarias para las reglas de dominio y la máquina de estados del agente, y de integración contra PostgreSQL en contenedor (Testcontainers) para la agenda, la atención y la auditoría. La API cuenta con 52 clases de prueba, la interfaz web con 18 y el agente con 6 módulos; todas se ejecutan antes de cada despliegue (apartado~\ref{sec:ob3_cicd}).
